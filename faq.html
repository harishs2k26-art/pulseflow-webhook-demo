Help / scope and limitations

Know what this webhook lab does—and does not do.

This public test site is a static educational fixture. Its local simulator is functional, but it is not evidence that a real webhook provider, receiver or network path is healthy.

Hosting and privacy

Can I point a real webhook provider at this GitHub Pages URL?

No. GitHub Pages serves static files and does not provide a request handler for arbitrary webhook POSTs. The inspector generates and verifies data locally; it never creates an inbound endpoint.

Where does my payload go?

The sandbox makes no network requests and uses no localStorage, cookies or analytics. Inputs and recent attempts remain in page memory until reset or reload. Still use invented data only: a public demonstration is not a safe place for real credentials or customer information.

Why is there no destination URL field?

A URL field would imply delivery or proxying that this static fixture does not implement. A production tool would need a backend, abuse controls, access restrictions and carefully defined retention.

Signatures and validation

Why does adding whitespace invalidate the signature?

HMAC authenticates bytes, not abstract JSON equality. Parsing and reserializing can change whitespace or key order. Verify the bounded raw body first, then parse and validate the event schema.

Can an old event have a fresh signature?

Yes. The event occurrence time is a business timestamp. A new delivery attempt signs its own current timestamp. Reject stale signing timestamps, not legitimate historical events being replayed.

Does a valid HMAC make the data safe?

No. It authenticates possession of a shared secret under this contract. You must still validate schema, authorization context, size and business rules. Never treat event text as executable code or trusted HTML.

Retries and duplicate processing

Why does a duplicate return 200 after I select 500?

If the local receiver previously processed the event successfully, its in-memory inbox acknowledges the duplicate without repeating work. Reset the inspector or change the event ID to test a new logical event. Real receivers need durable transactional deduplication.

Will the browser retry automatically?

No. Every attempt requires a button press. A simulated 429 displays a retry hint, but there are no timers, background jobs or network deliveries. The seven-attempt schedule in the overview is an illustrative service policy only.

How long should a receiver retain deduplication IDs?

The reference recommends at least 72 hours for a delivery window ending at 24 hours, with allowance for operational replay policies. Your actual retention must cover your real provider's maximum replay behavior and business requirements.

Operational practice

Before deploying a receiver, test clock skew, malformed headers, oversized bodies, secret rotation, repeated IDs and a crash after committing work but before acknowledging it. A two-step verify-and-enqueue design keeps expensive processing away from the synchronous request deadline.

Use the payload library, verification reference and CLI runbook to build a minimal, redacted diagnostic record. No support ticket or notification is sent from this page.
