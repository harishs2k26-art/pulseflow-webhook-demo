Try these scenarios

  1. Successful delivery: keep the defaults and simulate once. The receiver records the workspace/event pair in an in-memory inbox.
  2. Duplicate replay: submit again unchanged. The signature is checked again, but the pretend side effect is skipped and the duplicate is acknowledged.
  3. Receiver failure: reset, choose 500 and submit. Switch to 200 and retry the same event ID to complete processing.
  4. Rate limit: reset and choose 429. Inspect the five-second retry hint; the simulator does not wait or retry automatically.
  5. Invalid signature: reset and enable tampering. Even an extra newline changes the signed bytes and produces a simulated 401.
  6. Stale timestamp: reset and set the offset to -600. The HMAC can be valid while the freshness check fails.

Interpret the result carefully

A duplicate that was previously processed returns 200 even if the selected failure status is now 500; deduplication short-circuits repeated work. Failed attempts are not marked processed. Reloading or resetting clears the inbox, so this is not durable idempotency and must not be copied as a production persistence strategy.

The historical occurred_at value is allowed: freshness applies to the newly generated signing timestamp, not the event's business time. Validation checks the shared envelope, not every event-specific data field. A real receiver must validate the fields it uses.
